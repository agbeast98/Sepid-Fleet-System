# سند اجرایی تبدیل سامانه ناوگان سپید به برنامهٔ آنلاین

تاریخ تدوین: ۲۰ آبان ۱۴۰۵ — وضعیت بازبینی: ۲۳ آبان ۱۴۰۵؛ این سند مبنای اولیهٔ طراحی بود و بخش عمدهٔ سامانه اکنون پیاده‌سازی شده است. وضعیت واقعی در رودمپ تطبیق و ماتریس قابلیت‌ها ثبت می‌شود.

## وضعیت واقعی پیاده‌سازی

- فرانت React، Vite و TypeScript، بک‌اند NestJS، پایگاه مشترک PostgreSQL، نشست امن، مجوزهای سمت API، صف پایدار پیامک، OpenAPI، مهاجرت دادهٔ قدیمی و Compose/Nginx در پروژه وجود دارند.
- فرانت از مسیریابی داخلی سبک و لایهٔ API/حافظهٔ سفارشی استفاده می‌کند؛ React Router و TanStack Query در این نسخه نصب نشده‌اند. بک‌اند از SQL پارامتری با `pg` و migrationهای نسخه‌بندی‌شده استفاده می‌کند؛ Prisma استفاده نشده است. این تفاوت‌ها کارکرد سامانه را در آزمون‌های فعلی مختل نکرده‌اند، اما اگر انتخاب دقیق این کتابخانه‌ها الزام قراردادی باشد، هنوز انطباق کامل با سند نداریم.
- آزمون‌های API و سرتاسری Chrome و buildها در محیط ایزوله اجرا می‌شوند. انتقال عملیاتی نیازمند فایل پشتیبان واقعیِ کارفرما و پذیرش روی دامنه/سرور نهایی است؛ ارسال پیامک واقعی طبق محدودهٔ فعلی انجام نمی‌شود.
- برای فهرست اصلاحات فرانت و اختلاف‌های باقی‌مانده با نسخهٔ مرجع به `../sepid-fleet-system/ROADMAP-PARITY.fa.md` رجوع شود.

## ۱. هدف و محدوده

نسخهٔ موجود به یک سامانهٔ چندکاربره با فرانت‌اند مبتنی بر فریم‌ورک، بک‌اند مستقل و پایگاه دادهٔ مشترک تبدیل شود. قابلیت‌های موجود، رابط فارسی، راست‌چین، فونت وزیرمتن، تاریخ شمسی، چاپ و کاربرد موبایل حفظ شوند. توسعه بر اساس رفتار فعلی انجام شود؛ تغییر قواعد کسب‌وکار باید جداگانه ثبت و تأیید شود.

این پروژه شامل توسعهٔ نرم‌افزار و اتصال فرانت و بک‌اند است؛ استقرار و تنظیم سرور تنها یکی از مراحل آن است. صرف آپلود فایل‌ها یا ساخت دیتابیس، نسخهٔ فعلی را چندکاربره نمی‌کند.

خارج از محدودهٔ اولیه: GPS زنده، اپلیکیشن موبایل مستقل، حسابداری، مدیریت موجودی انبار و همگام‌سازی آفلاین. ثبت قطعات جایگزین به معنی وجود سیستم انبارداری نیست.

## ۲. مبنای موجود و میزان قطعیت

منابع مرجع: `README.md`، `assets/js/app.js`، `assets/css/style.css` و نسخهٔ تک‌فایلی در `original`.

موارد تأییدشده از کد و راهنما:

- برنامه با HTML، CSS و JavaScript خالص ساخته شده و مسیریابی hash دارد.
- داده‌ها یک شیء با `schema: 4` هستند؛ در IndexedDB با نام `fleet-maint-app`، مخزن `kv` و کلید `db` نگه‌داری می‌شوند. مسیر جایگزین، localStorage است.
- `seedDB()` برخی ماشین‌ها، مدل‌ها و پرسنل را داخل کد تعریف می‌کند. سوابق اولیهٔ تعمیر، تحلیل، سرویس و کارکرد خالی هستند. پروندهٔ مشخصات ماشین با پروندهٔ خرابی تفاوت دارد.
- ورود، مجوزها و پیامک در مرورگر پیاده شده‌اند. نسخهٔ آنلاین باید مرجع تصمیم‌گیری را به سرور منتقل کند.
- سطح دسترسی بخش‌ها از صفر تا سه است، با سقف متفاوت برای بعضی بخش‌ها. مجوز مرحله و محدودیت تعمیرگاه نیز وجود دارند.

این سند جای ممیزی کامل کد را نمی‌گیرد. پیش از ساخت هر ماژول، فیلدها، اعتبارسنجی‌ها، محاسبات و رفتارهای آن از کد استخراج و در یک جدول تطبیق ثبت شوند. هیچ فیلدی فقط به دلیل نیامدن در جدول پیشنهادی این سند حذف نشود.

## ۳. معماری و فناوری منتخب برای این طرح

برای یکسان بودن زبان توسعه، مبنای اجرایی این سند TypeScript در فرانت و بک‌اند است:

| بخش | انتخاب | مسئولیت |
|---|---|---|
| فرانت‌اند | React + Vite + TypeScript | صفحه‌ها، فرم‌ها و تعامل کاربر |
| مسیریابی | React Router | مسیرهای صفحه و حفاظت نمایشی مسیرها |
| دادهٔ سمت کاربر | TanStack Query | دریافت، کش و تازه‌سازی پاسخ API |
| بک‌اند | NestJS + TypeScript | API، اعتبارسنجی، مجوزها و قواعد کسب‌وکار |
| دیتابیس | PostgreSQL | نگه‌داری مشترک و تراکنش‌ها |
| دسترسی دیتابیس | Prisma و migrationهای نسخه‌بندی‌شده | مدل‌ها و تغییرات ساختار |
| قرارداد | OpenAPI | مستندات API و تولید کلاینت تایپ‌شده |
| استقرار | Docker Compose + Nginx | اجرای سرویس‌ها و HTTPS |
| کارهای پس‌زمینه | worker با صف ماندگار در PostgreSQL | ارسال و پیگیری پیامک |

این جدول انتخاب اولیهٔ طراحی است. پیاده‌سازی فعلی در موارد مسیریابی، cache سمت کاربر و دسترسی SQL با شرح بالا تفاوت دارد؛ پیش از الزام به مهاجرت فنی، باید ارزش این تغییر نسبت به وضعیت کارکردی و آزموده‌شده سنجیده شود. نسخهٔ دقیق وابستگی‌ها در lockfile و تصاویر کانتینر تثبیت شده است.

مرورگر از یک دامنه، فایل‌های فرانت و مسیر `/api/v1` را دریافت می‌کند. Nginx درخواست API را به بک‌اند می‌فرستد. فقط بک‌اند و worker به دیتابیس و کلیدهای پیامک دسترسی دارند.

ساختار پیشنهادی:

```text
apps/web/               React
apps/api/               NestJS
packages/api-client/    کلاینت تولیدشده از OpenAPI
infra/                  Compose، Nginx و نمونهٔ تنظیمات
docs/                   مدل داده، قواعد و راهنمای بهره‌برداری
```

سورس فعلی تا پایان تطبیق قابلیت‌ها به‌عنوان مرجع حفظ شود. فرانت جدید به مرورگر اجازهٔ اجرای مستقیم کد قدیمی به‌عنوان لایهٔ ذخیره‌سازی ندهد.

## ۵. طراحی پیشنهادی دیتابیس

جدول‌های زیر نقطهٔ شروع‌اند؛ جزئیات نهایی باید از تمام فرم‌ها و توابع فعلی استخراج شوند.

| جدول یا مجموعه | داده و رابطهٔ اصلی |
|---|---|
| users، sessions | کاربران، هش رمز جدید، وضعیت و نشست‌های قابل ابطال |
| user_section_permissions | کاربر، بخش، سطح دسترسی با رعایت سقف بخش |
| user_stage_permissions | مراحل مجاز هر کاربر |
| people | پرسنل، نقش، تلفن، توضیحات و وضعیت |
| machine_models، machines | مدل و ماشین، مسئولان، واحد کارکرد و مشخصات |
| model_parts، part_alternatives | قطعات هر مدل و گزینه‌های جایگزین |
| odometer_logs | ماشین، مقدار، واحد، زمان و ثبت‌کننده |
| part_logs | سرویس/تعویض قطعه و اطلاعات مبنای محاسبهٔ نگهداری |
| repairs | پروندهٔ خرابی، ماشین، فوریت و وضعیت جاری |
| stage_definitions، repair_events | تعریف مراحل و تاریخچهٔ ثبت مرحله با ثبت‌کننده |
| analyses، management_rules | تحلیل‌ها و قواعد اقدامات مدیریتی |
| app_settings | تنظیمات عمومی و تنظیمات قابل تغییر |
| sms_rules، sms_messages، sms_attempts | قالب و گیرندگان، صف ارسال و هر تلاش ارسال |
| audit_logs، import_batches | ثبت تغییرات مهم و سابقهٔ ورود داده |

قواعد طراحی:

- کلید خارجی و شاخص مناسب برای ماشین، تاریخ، وضعیت و روابط پرتکرار تعریف شود.
- شناسهٔ قدیمی در مهاجرت حفظ یا در جدول نگاشت ثبت شود تا ارتباط رکوردها از بین نرود.
- رکوردهای قابل ویرایش، نسخهٔ عددی و زمان ایجاد/ویرایش داشته باشند.
- زمان رویدادها به UTC ذخیره شود؛ تاریخ‌های صرفاً روزانه با نوع DATE نگه‌داری شوند. تبدیل شمسی در نمایش/ورودی و مرز API تعریف شود تا تغییر منطقهٔ زمانی روز را جابه‌جا نکند.
- روابط تاریخی با حذف پرسنل یا ماشین از بین نروند. سیاست حذف نرم و محدودیت حذف برای هر موجودیت مشخص شود.
- واحد کیلومتر و ساعت کار مخلوط نشود. قواعد اصلاح کارکرد و مقدار کاهشی از کد و فرایند واقعی استخراج شوند.
- JSON فقط برای تنظیمات یا دادهٔ انعطاف‌پذیر استفاده شود؛ کل سامانه یک رکورد JSON قابل بازنویسی نباشد.
- فیلد `scopeShop` و معنای دقیق محدودهٔ تعمیرگاه پیش از طراحی روابط نهایی بررسی شود؛ صرف نام فیلد برای فرض کردن ساختار تعمیرگاه کافی نیست.

## ۶. قرارداد API

پیشوند همهٔ مسیرها `/api/v1` است. پاسخ‌ها فقط دادهٔ مجاز کاربر را برگردانند. فهرست‌ها صفحه‌بندی، مرتب‌سازی با فیلدهای مجاز و فیلتر معتبر داشته باشند.

| مسیر پیشنهادی | عملیات |
|---|---|
| `/auth/login`, `/auth/logout`, `/auth/me` | نشست و کاربر جاری |
| `/users`, `/users/:id/permissions` | مدیریت کاربران و دسترسی‌ها |
| `/machines`, `/machines/:id` | فهرست و مشخصات ماشین |
| `/people`, `/models`, `/parts` | اطلاعات پایه |
| `/machines/:id/odometer-logs` | کارکرد |
| `/machines/:id/part-logs` | سرویس و تعویض قطعه |
| `/maintenance` | وضعیت و موعد نگهداری محاسبه‌شده |
| `/repairs`, `/repairs/:id` | پروندهٔ خرابی |
| `/repairs/:id/events` | ثبت و خواندن مرحله‌ها |
| `/repairs/:id/events/:eventId/revert` | برگشت کنترل‌شدهٔ آخرین ثبت |
| `/analyses`, `/management-rules` | تحلیل و قواعد |
| `/dashboard`, `/reports/*` | خروجی‌های گزارش |
| `/settings`, `/stage-definitions` | تنظیمات عمومی و مراحل |
| `/sms/rules`, `/sms/messages`, `/sms/test` | پیامک و گزارش آن |
| `/imports/preview`, `/imports/:id/commit` | پیش‌نمایش و اجرای مهاجرت داده |
| `/exports` | خروجی داده بر اساس مجوز |

برای هر مسیر، DTO درخواست/پاسخ، قواعد اعتبارسنجی، سطح دسترسی و خطاها در OpenAPI تعریف شود. خطاها شامل کد پایدار، پیام قابل نمایش و خطای فیلد باشند؛ اطلاعات داخلی و رمزها نمایش داده نشوند.

ویرایش با نسخهٔ رکورد انجام شود. اگر نسخه قدیمی بود سرور `409` برگرداند و فرانت امکان دریافت آخرین داده و اعمال مجدد تغییر را بدهد. ثبت مرحله و ارسال آزمایشی پیامک، کلید idempotency داشته باشند تا تکرار درخواست، عملیات تکراری نسازد.

ثبت مرحله، به‌روزرسانی وضعیت، audit و ایجاد پیام در outbox در یک تراکنش انجام شوند. ارسال پیامک خارج تراکنش انجام شود. شکست پیامک نباید ثبت تعمیر را لغو کند.

## ۷. ورود و مجوزها

- نشست سمت سرور با کوکی HttpOnly، Secure و SameSite مناسب پیاده شود؛ خروج و غیرفعال‌سازی کاربر نشست را باطل کند.
- محافظت CSRF برای عملیات تغییردهنده، محدودیت تلاش ورود و ثبت رخدادهای ورود اعمال شود.
- رمزهای جدید با Argon2id هش شوند. هش‌ها و salt قدیمی در پاسخ عمومی یا خروجی معمولی قرار نگیرند.
- کنترل مجوز در تمام APIها انجام شود: سطح بخش، مرحلهٔ مجاز، محدودهٔ رکورد و وضعیت فعال کاربر. پنهان کردن دکمه در فرانت کافی نیست.
- الگوهای سرپرست، تعمیرات، تست سلامت و مشاهده‌گر از کد فعلی منتقل شوند؛ امکان مجوز سفارشی حفظ شود.
- مدیر کل بر اساس نقش شناسایی شود، نه نام شخص. ایجاد اولین مدیر با فرایند یک‌باره و بدون رمز پیش‌فرض عمومی انجام شود.
- برای مهاجرت کاربران، حساب‌ها با ارتباطاتشان وارد شوند، اما رمز جدید از مسیر فعال‌سازی امن تعیین شود. هش قدیمی بدون طراحی صریح سازگاری به‌عنوان هش جدید پذیرفته نشود.

## ۸. پیامک

لایهٔ provider برای کاوه‌نگار، sms.ir و در صورت نیاز مقصد سفارشی تعریف شود. قرارداد واقعی سرویس انتخابی هنگام اتصال بررسی شود. کلیدها در secrets سرور نگه‌داری شوند؛ فرانت فقط وضعیت تنظیم بودن را ببیند.

worker پیام‌های صف را با قفل/claim اتمیک دریافت کند. قواعد گیرنده، جلوگیری از ارسال به ثبت‌کننده، کاربران دریافت‌کنندهٔ همهٔ پیامک‌ها و قالب‌های فعلی پس از استخراج دقیق حفظ شوند.

وضعیت‌های در صف، در حال ارسال، پذیرفته‌شده توسط سرویس، نامشخص، ناموفق و تحویل‌شده از هم تفکیک شوند. «تحویل‌شده» فقط با مدرک سرویس ثبت شود. در timeout، ارسال مجدد کور ممکن است پیام تکراری ایجاد کند؛ ابتدا شناسه و وضعیت سرویس بررسی شود. تعداد تلاش، تأخیر و سقف ارسال کنترل شود.

در توسعه از provider ساختگی استفاده شود. ارسال واقعی و هزینه‌دار فقط در مرحلهٔ پذیرش مجاز انجام شود. مقصد سفارشی به میزبان‌های مجاز محدود شود تا API به مسیر درخواست آزاد به شبکهٔ داخلی تبدیل نشود.

## ۹. مهاجرت دادهٔ مرورگر

۱. از نسخهٔ فعلی خروجی JSON تهیه و نسخهٔ اصلی بدون تغییر نگه‌داری شود. پاک‌سازی دادهٔ مرورگر انجام نشود.

۲. ابزار مهاجرت فایل را اعتبارسنجی کند؛ نسخه‌های قدیمی مطابق رفتار `migrate` ارتقا یابند. کد مهاجرت از وابستگی به DOM جدا شود.

۳. پیش‌نمایش تعداد ماشین‌ها، افراد، تعمیرات، رویدادها و روابط نامعتبر نمایش داده شود. فیلد ناشناخته نباید بی‌صدا حذف شود.

۴. در مرحلهٔ نخست ورود کامل فقط به دیتابیس خالی مجاز باشد؛ ادغام با دادهٔ فعال یک قابلیت جداست. شناسهٔ batch و اثر انگشت فایل از ورود تکراری جلوگیری کنند.

۵. تبدیل و ورود داده تراکنشی باشد. شکست نباید دیتابیس نیمه‌واردشده باقی بگذارد. کلیدهای پیامک و اعتبارنامه‌های قدیمی از مسیر عمومی ورود حذف و جداگانه مدیریت شوند.

۶. شمار رکوردها، روابط و نمونهٔ گزارش‌ها قبل و بعد مقایسه شوند. داده‌های پایهٔ هاردکدشده خودکار به دادهٔ عملیاتی اضافه نشوند؛ seed نمایشی فقط با گزینهٔ صریح محیط توسعه فعال شود.

۷. هنگام انتقال نهایی، ثبت در نسخهٔ قدیمی متوقف، آخرین خروجی وارد و سپس استفاده از نسخهٔ آنلاین آغاز شود. همگام‌سازی دوطرفهٔ نسخهٔ قدیمی و جدید در این طرح وجود ندارد.

## ۱۰. پیاده‌سازی فرانت‌اند

صفحه‌ها به component، فرم، hook و سرویس API تقسیم شوند. CSS و فونت‌های موجود مبنای حفظ ظاهر باشند. ابتدا shell، منو، ورود و اطلاعات پایه منتقل شوند؛ سپس تعمیرات و سایر حوزه‌ها.

مرجع دادهٔ عملیاتی API باشد. کش فرانت جایگزین دیتابیس نیست. در قطع ارتباط، وضعیت اتصال و شکست ذخیره واضح نشان داده شود؛ موفقیت ذخیره فقط پس از تأیید سرور اعلام شود. ذخیرهٔ آفلاین خودکار در این مرحله پیاده نشود.

برای دیده شدن تغییر کاربران دیگر، در شروع تازه‌سازی دوره‌ای صفحهٔ فعال و تازه‌سازی پس از عملیات کافی است؛ فاصلهٔ آن تنظیم‌پذیر باشد. بعداً در صورت نیاز SSE اضافه شود. پاسخ‌های کاربران مختلف یا نشست قبلی در کش مخلوط نشوند.

ورودی شمسی، اعداد فارسی، نمایش موبایل، چاپ و تم‌ها حفظ شوند. HTML تولیدشده از دادهٔ کاربر بدون escape رندر نشود.

## ۱۱. مراحل اجرا و خروجی هر مرحله

| مرحله | کار | شرط اتمام |
|---|---|---|
| صفر | استخراج فرم‌ها، قواعد، مجوزها و داده‌ها | جدول تطبیق قابلیت‌ها و پرسش‌های کسب‌وکار |
| یک | ساختار پروژه، دیتابیس، migration و محیط محلی | اجرای مستند فرانت و API و healthcheck |
| دو | نشست، کاربران و مجوزها | اعمال دسترسی در سرور و فرانت |
| سه | پرسنل، مدل‌ها و ماشین‌ها | عملیات پایه و روابط معتبر |
| چهار | خرابی، مراحل و تاریخچه | گردش کامل و کنترل هم‌زمانی |
| پنج | نگهداری، قطعات، تحلیل و گزارش | تطبیق محاسبات با مرجع فعلی |
| شش | پیامک و worker | صف ماندگار، ثبت تلاش‌ها و مدیریت خطا |
| هفت | مهاجرت و خروجی | ورود نمونهٔ واقعی با تطبیق تعداد و روابط |
| هشت | استقرار آزمایشی و پذیرش | سناریوهای زیر و راهنمای عملیات |

در هر مرحله فرانت و بک‌اند همان قابلیت با هم کامل شوند. ساخت تعداد زیادی endpoint بدون صفحهٔ متصل، پایان یک قابلیت محسوب نمی‌شود.

## ۱۲. معیار پذیرش

- ثبت در مرورگر اول پس از تازه‌سازی در مرورگر دوم دیده شود؛ پاک شدن کش مرورگر دادهٔ سرور را حذف نکند.
- دست‌کاری درخواست مستقیم توسط کاربر بدون مجوز با خطای دسترسی متوقف شود؛ محدودیت رکورد و مرحله نیز بررسی شود.
- دو ویرایش هم‌زمان باعث حذف بی‌خبر تغییر دیگری نشوند.
- ثبت تکراری یک درخواست، رویداد یا پیامک اضافی تولید نکند؛ شرایط مبهم سرویس پیامک جداگانه پوشش داده شوند.
- تاریخچهٔ وضعیت، ثبت‌کننده و برگشت عملیات قابل ردیابی باشند.
- محاسبهٔ نگهداری، گزارش‌ها و تاریخ‌های مرزی شمسی با دادهٔ یکسان با نسخهٔ مرجع مقایسه شوند.
- ورود دادهٔ معیوب اثری روی دیتابیس نگذارد و ورود دوبارهٔ همان batch جلوگیری شود.
- رمز و کلید پیامک در پاسخ API، فایل فرانت، لاگ یا خروجی عادی نباشد.
- بازیابی یک بکاپ روی محیط جدا عملاً موفق شود.
- مسیرهای اصلی در موبایل، RTL و چاپ قابل استفاده باشند.

آزمون‌ها شامل واحد برای قواعد و تاریخ، یکپارچه برای تراکنش و مجوز و migration، و سرتاسری برای ورود تا ثبت و پایان تعمیر باشند. داده و پیامک آزمون از محیط عملیاتی جدا باشند.

## ۱۳. استقرار و بهره‌برداری

سرویس‌های web، api، worker و postgres با Compose تعریف شوند. دیتابیس پورت عمومی نداشته باشد و volume پایدار داشته باشد. HTTPS، اندازهٔ مجاز درخواست، health/readiness، گردش لاگ و راه‌اندازی مجدد سرویس‌ها تنظیم شوند.

فایل نمونهٔ env بدون secret ارائه شود. secrets وارد Git یا image نشوند. CI باید نصب تکرارپذیر، typecheck، lint، آزمون و build را اجرا کند. migrationها پیش از انتشار در محیط آزمایشی اجرا شوند.

پشتیبان خودکار دیتابیس خارج از سرور اصلی نگه‌داری شود؛ دوره و مدت نگه‌داری با نیاز شرکت تعیین شود. پایش حداقل شامل سلامت سرویس، خطاهای API، فضای دیسک، سن صف پیامک و موفقیت بکاپ باشد.

قبل از تغییر ساختار، بکاپ گرفته شود. طرح بازگشت باید سازگاری نسخهٔ قبلی برنامه با ساختار جدید و احتمال از دست رفتن دادهٔ بعد از بکاپ را مشخص کند؛ صرف بازگرداندن image برای هر migration کافی نیست.

## ۱۴. اطلاعات لازم از کارفرما پیش از انتشار عملیاتی

تعداد کاربران و میزان استفادهٔ هم‌زمان، محدودهٔ تعمیرگاه‌ها، قواعد واقعی تغییر مرحله و برگشت، نمونهٔ خروجی دادهٔ واقعی، سرویس پیامک و سقف هزینه، دامنه و زیرساخت، مسئول مدیر کل، دورهٔ بکاپ و تحمل از دست رفتن داده مشخص شوند.

نبود این پاسخ‌ها مانع استخراج کد و ساخت محیط توسعه نیست؛ تصمیم‌های وابسته در سند تصمیم‌ها ثبت شوند و پیش از انتشار قطعی شوند.

## ۱۵. تحویل نهایی

سورس فرانت و بک‌اند، schema و migration دیتابیس، قرارداد OpenAPI، ابزار مهاجرت، تنظیمات استقرار بدون رمز، راهنمای اجرای محلی و سرور، راهنمای بکاپ و بازیابی، گزارش آزمون‌ها و جدول تطبیق قابلیت‌ها تحویل داده شوند.

تعریف پایان کار: تمام قابلیت‌های توافق‌شده از طریق API و دیتابیس مشترک کار کنند، دسترسی‌ها سمت سرور اعمال شوند، دادهٔ فعلی قابل انتقال باشد و اجرای دوبارهٔ پروژه روی محیط تازه طبق راهنما امکان‌پذیر باشد.
