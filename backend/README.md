# بک‌اند سامانه ناوگان سپید

این پوشه شامل پروژهٔ NestJS، پیکربندی PostgreSQL و SQL اولیه است. اجرای محلی به Node.js نسخهٔ 24.7 یا بالاتر از شاخهٔ 24 نیاز دارد؛ ارسال صف پیامک در توسعه همراه API اجرا می‌شود و در Compose تولید worker جداگانه دارد.

۱. از همین پوشه `npm install` را اجرا کنید.

۲. متغیر محیطی `SEPID_POSTGRES_PASSWORD` را با رمز توسعه تنظیم کنید و از همین پوشه `docker compose up -d --wait postgres` را اجرا کنید. Compose اسکریپت SQL را هنگام ایجاد دیتابیس روی volume تازه اجرا می‌کند.

۳. از `.env.example` یک فایل `.env` بسازید و رمز `DATABASE_URL` را با رمز PostgreSQL یکسان کنید. کاراکترهای خاص رمز را در URL به شکل percent-encoded بنویسید.

۴. با `npm run dev` بک‌اند را اجرا کنید. این دستور ابتدا migrationهای توسعه را اجرا می‌کند. فرانت توسعه روی پورت ۵۵۳۲۱ و API روی پورت ۵۵۳۲۰ در دسترس‌اند تا با سرویس‌های رایج محلی تداخل نکنند. مسیر `/api/v1/health/ready` اتصال و آماده بودن جدول‌های تعمیرات و قطعات را بررسی می‌کند.

برای ساخت نخستین مدیر در محیط توسعه، هنگام اجرای بک‌اند متغیرهای `SEPID_ADMIN_USERNAME` و `SEPID_ADMIN_PASSWORD` را تنظیم کنید. رمز باید دست‌کم ۱۲ کاراکتر داشته باشد. پس از اولین اجرای موفق متغیرهای موقت را پاک کنید. اگر مدیر کل وجود داشته باشد، اجرای مجدد رمز او را تغییر نمی‌دهد.

ورود، خروج، مدیریت کاربران و مجوزها، ماشین‌ها، مدل‌ها و پرسنل فعال‌اند. پروندهٔ ماشین می‌تواند به مدل، راننده، سرپرست و مسئول نگهداری مرتبط شود. تعمیرات از مرحله‌های مشترکِ قابل‌تنظیم، تاریخچه، برگشت کنترل‌شدهٔ آخرین تغییر و بایگانی نتیجهٔ تست پشتیبانی می‌کند. نسخهٔ پرونده، مجوز مرحله و محدودهٔ داده در سرور بررسی می‌شوند.

API نگهداری، تاریخچهٔ کارکرد و سرویس را ذخیره می‌کند و موعد هر قطعه را با دورهٔ کیلومتری، ساعتی یا ماهانه محاسبه می‌کند. فهرست قطعات و جایگزین‌ها، تحلیل خرابی و قواعد اقدام مدیریتی، داشبورد، گزارش چاپی/CSV، تنظیمات و پشتیبان سرور نیز به API وصل‌اند.

گزارش تعمیرات با چاپ و CSV، تنظیمات مشترک، تحلیل‌های پایه، بازیابی نسخهٔ JSON در محیط سازگار و صف پایدار پیامک پیاده شده‌اند. تنظیم پیامک هر مرحله، گیرنده‌ها و قالب متغیردار در PostgreSQL نگه‌داری می‌شود؛ پیام هنگام ثبت رویداد تعمیر در تراکنش صف می‌شود. گیرنده‌های همگانیِ انتخاب‌شده در حساب‌ها همیشه در اعلان مرحله‌ای هستند و می‌توان سرپرست، مسئول PM و مدیر کل را هم برای هر مرحله جداگانه انتخاب کرد. حساب کاربر به پروندهٔ پرسنلی وصل می‌شود تا شمارهٔ ثبت‌شدهٔ همان کاربر برای اعلان سرپرست/PM استفاده شود. پنل ارسال دستی آزمایشی هم دارد. محیط توسعه به‌طور پیش‌فرض از شبیه‌ساز استفاده می‌کند و worker آن کنار API اجرا می‌شود؛ در Compose تولید، worker سرویس جداگانه است. برای فعال‌کردن فرستندهٔ کاوه‌نگار در سرور، `SMS_PROVIDER=kavenegar` و `KAVENEGAR_API_KEY` و `KAVENEGAR_SENDER` را فقط در فایل محیطی بک‌اند تنظیم کنید. پاسخ پذیرفته‌شده از سرویس تضمین تحویل به گوشی نیست؛ timeout با وضعیت نامشخص ثبت می‌شود تا از ارسال تکراری ناخواسته جلوگیری شود.

روی پایگاه‌دادهٔ کاملاً خالی، migration یازدهم فهرست آغازین ۱۱ ماشین، ۷ مدل و ۹ پرسنل را از دادهٔ seed نسخهٔ اصلی وارد می‌کند. اگر جدول‌های ناوگان یا فضای سازگاری از قبل داده داشته باشند، این seed اجرا نمی‌شود. این فهرست دادهٔ اولیهٔ برنامه است و جایگزین پشتیبان/دادهٔ واقعی IndexedDB نیست.

تطبیق تصویری و رفتاری مو‌به‌مو با نسخهٔ قبلی هنوز کامل نشده است. انتقال یک‌بارهٔ JSON قدیمی به جداول رابطه‌ای از صفحهٔ مدیر، با پیش‌نمایش و کنترل سازگاری، پیاده شده؛ اما فایل واقعی کاربر در این محیط موجود نیست تا تعداد و روابط دادهٔ او تطبیق داده شوند. راه‌اندازی SMS واقعی به کلید/فرستندهٔ شرکت و آزمون موردتوافق نیاز دارد؛ تست‌های مرورگر و آزمون Compose از شبیه‌ساز استفاده می‌کنند و پیام واقعی نمی‌فرستند. ساخت و اجرای یک‌پارچهٔ imageهای production در Compose با PostgreSQL تازه، وب، API آماده، worker پیامک و پشتیبان اعتبارسنجی‌شده در محیط محلی ایزوله بررسی شده؛ استقرار روی میزبان مقصد، دامنه/HTTPS، پشتیبان خارج از میزبان و تمرین بازیابی دادهٔ واقعی هنوز در مقصد انجام نشده‌اند.

مسیر سازگاری `/api/v1/legacy-workspace` از نشست مدیر کل استفاده می‌کند و دادهٔ نسخهٔ اصلی را به شکل JSONB نگه می‌دارد. کنترل نسخه از بازنویسی ناخواسته جلوگیری می‌کند. حساب‌های قدیمی و تنظیمات اتصال پیامک وارد این داده نمی‌شوند. این فضای سازگاری پس از انتقال نیز مستقل از جداول عملیاتی React می‌ماند؛ برای کار روزمرهٔ نسخهٔ جدید، پرونده‌ها از جداول رابطه‌ای خوانده می‌شوند.

برای آزمون API، از همین پوشه `npm run test:api` را اجرا کنید. این تست schema موقتی می‌سازد، اسکریپت مهاجرت production را روی همان پایگاه خالی اجرا می‌کند، سناریوهای API را می‌سنجد و پس از بررسی آن را حذف می‌کند. آزمون کامل مرورگر با `npm run test:browser` اجرا می‌شود؛ Chrome یا Edge باید نصب باشد و متغیر `CHROME_BIN` به فایل اجرایی مرورگر اشاره کند. این آزمون نیز فقط schema موقت می‌سازد و پس از پایان حذف می‌کند.

مسیرهای `apps/web` و `apps/api` در [سند اجرایی](IMPLEMENTATION-PLAN.fa.md) به‌ترتیب معادل پوشه‌های مستقل `frontend` و `backend` هستند.

اتصال IPPanel Edge شامل ارسال متنی، ارسال Pattern، دریافت Patternهای فعال پنل، استعلام گزارش هر پیام و OTP ورود است. راهنمای پیکربندی و منابع رسمی در [`docs/ippanel-setup.fa.md`](../docs/ippanel-setup.fa.md) قرار دارد. برای متغیرهای محیطی از `IPPANEL_API_KEY` و `IPPANEL_SENDER` استفاده می‌شود؛ هر دو باید فقط به API و worker برسند.
