# پیگیری تطبیق قابلیت‌های سامانه

این جدول وضعیت پیاده‌سازی فعلی را ثبت می‌کند. وجود صفحه یا مسیر API به‌تنهایی به معنی تطبیق کامل با سامانهٔ مرجع نیست.

برای اختلاف‌های دیداری صفحه‌به‌صفحه، اولویت‌بندی کارهای باقی‌مانده و معیار پایان، [ممیزی و رودمپ تطبیق](ROADMAP-PARITY.fa.md) را ببینید.

آخرین build فرانت و آزمون جامع Chrome در ۱۵ نوامبر ۲۰۲۶ موفق شدند؛ آزمون از PostgreSQL ایزوله استفاده می‌کند. Chrome گردش ورود، ناوبری، تعمیرات، نگهداری، قطعات، تحلیل و اقدام‌ها، گزارش، بایگانی، انتقال، پشتیبان، پیامک شبیه‌سازی‌شده و موبایل را بررسی می‌کند. در آزمون فعلی، ارتفاع کامل داشبورد، اقدامات، پرسنل و وضعیت حداکثر ۲ پیکسل، راهنما و نگهداری حداکثر ۳ پیکسل با مرجع اختلاف دارند. بخش‌های پایین داشبورد با تلورانس مشخص کنترل می‌شوند. کارت‌های انتخاب ماشین در نگهداری جهت فلش و نشان‌های آیکن‌دار نسخهٔ مرجع را دارند؛ کارت‌های اقدامات هم ترتیب و نشان‌ها و ارتفاع کلی را کنترل می‌کنند. تصاویر همهٔ نماها ذخیره می‌شوند، اما تأیید تک‌تک رنگ‌ها و جزئیات، فرم‌ها و پنجره‌ها، پوستهٔ تاریک/روشن و همهٔ حالت‌های موبایل همچنان باز است. فایل پشتیبان عملیاتی و پذیرش روی میزبان/دامنهٔ مقصد در دسترس نیست. تفاوت دسترسی صفحهٔ پیامک مرجع محدودیت مقایسه است. ارسال واقعی پیامک خارج از دامنه است. جزئیات و وابستگی‌های استقرار در [رودمپ تطبیق](ROADMAP-PARITY.fa.md) ثبت شده‌اند.

در مقایسهٔ تصویری تنظیمات روشن، آیکن زبانهٔ «عمومی» به آیکن لغزنده‌های نسخهٔ مرجع تغییر کرد؛ آزمون Chrome شکل SVG را بررسی می‌کند و پس از اصلاح موفق گذشت.

در بازبینی تصویری جدید، ترتیب جایگاه دکمه‌های بایگانی/چاپ/خروجی در صفحهٔ خرابی‌های جاری، پیام کارت KPI خالی داشبورد، آیکن عنوان بخش تحلیل و فاصلهٔ بالای گروه نخست اقدامات مدیریتی با مرجع هم‌راستا شدند. در فهرست پرسنل نیز فیلتر اضافه حذف شد و جدول‌ها در کارت‌های گروهی مرجع قرار گرفتند. آزمون Chrome ترتیب افقی دکمه‌ها، متن حالت خالی داشبورد و نبود فیلتر اضافه را صریح بررسی می‌کند.

در ادامهٔ بازبینی پوسته، نشانگرهای منوی وضعیت، خرابی‌های در جریان، نگهداری و پشتیبان با منطق نسخهٔ مرجع و دادهٔ API هماهنگ شدند. شمار خرابی‌های باز/دیرکرددار و قطعات گذشته از موعد در منو دیده می‌شود؛ هشدار پشتیبان برای مدیر هم نقطهٔ زرد دارد. Chrome وجود عدد و رنگ قرمز در خرابی دیرکرددار را تأیید کرد؛ ساخت فرانت و بک‌اند نیز موفق بود.

دکمهٔ «تغییر رمز من» هم به کارت کاربر برگشت. تغییر رمز، رمز فعلی را می‌خواهد، نشست همین مرورگر را نگه می‌دارد و نشست‌های دیگر را باطل می‌کند؛ رمز باید دست‌کم ۱۲ نویسه داشته باشد.

در دور تازهٔ داشبورد، نمودار مقایسه به ستون‌های گروهی نسخهٔ مرجع برگشت و نمودار ماهانه حالا دو سری خطی، مقیاس، نقاط و برچسب‌های دوازده‌ماهه را نشان می‌دهد؛ حالت خالی نیز همان محورهای صفر را نگه می‌دارد. آزمون Chrome حالت بی‌داده و داده‌دار را بررسی می‌کند. مقایسهٔ تصویری مستقیم همین خروجی تازه با تصویر هم‌شرایط مرجع هنوز باید انجام شود.

## بررسی انجام‌شده

- عنوان، توضیح و دکمه‌های اصلی در صفحه‌های ماشین، تحلیل، اقدامات مدیریتی، پرسنل، کاربران، نگهداری، قطعات، پیامک و مهاجرت به الگوی سربرگ بیرون کارت انتقال یافتند؛ آزمون کامل Chrome پس از هماهنگ‌کردن انتظارهای سربرگ/خروجی، موفق شد. این آزمون کارکرد را می‌سنجد و تطبیق پیکسل‌به‌پیکسل با صفحه‌های قدیمی را ثابت نمی‌کند.
- تقویم شمسی قدیمی به فیلترها و فرم‌های تاریخ منتقل شد؛ API همچنان تاریخ میلادی ISO دریافت می‌کند. آزمون Chrome ورودی ۱۴۰۵/۰۸/۱۰ و ثبت تاریخ ۲۰۲۶/۱۱/۰۱ در پایگاه‌داده را تأیید کرد. تصاویر تمام‌قد آزمون از بالای صفحه ثبت می‌شوند.
- ساخت فرانت و بک‌اند با موفقیت انجام شد.
- داشبورد React از APIهای تعمیر، تحلیل و نگهداری که سطح دسترسی همان کاربر را رعایت می‌کنند خلاصه می‌گیرد؛ تعمیرات باز، موعدهای گذشته، آخرین تحلیل‌ها و هشدار قطعات را نشان می‌دهد. فیلتر راننده، ماشین و بازه و نمودارهای نتیجه، مقایسهٔ ماشین و روند ۱۲ماهه هم اضافه و با Chrome بررسی شدند.
- ساخت مجدد imageهای Docker فرانت و بک‌اند و اعتبارسنجی هر دو Compose موفق بود. این بررسی به‌تنهایی استقرار روی سرور مقصد یا پشتیبان‌گیری عملیاتی را انجام نمی‌دهد.
- آزمون API با schema موقت موفق بود: اجرای migrationها، دادهٔ آغازین، ورود مدیر آزمایشی، ذخیرهٔ نام شرکت و همگام‌سازی تنظیمات سازگاری. این آزمون داده‌های پایگاه‌دادهٔ توسعه را تغییر نمی‌دهد.
- آزمون API با schema موقت، انتقال کامل یک پشتیبان نسخهٔ ۴ شامل مرحله‌های سفارشی، تاریخ شمسی، ماشین، قطعه/جایگزین، سابقهٔ سرویس و کارکرد، خرابی/رویداد و تحلیل را اجرا کرد؛ شمارش و تاریخ واردشده کنترل شدند و دادهٔ آزمایشی پس از بررسی پاک شد.
- آزمون Chrome روی صفحهٔ مدیر، صفحهٔ پیش‌نمایش انتقال را هم در حالت نبود پشتیبان باز کرد؛ کل سناریوی مرورگر پس از اضافه‌شدن migrationهای ۱۷ تا ۲۰ دوباره موفق شد.
- سلامت API توسعه `ready` و پاسخ صفحهٔ فرانت `200` بررسی شد.
- فرم اعلام خرابی در React به انتخاب کارت‌مانند ماشین و انتخاب بصری سطح فوریت با مهلت اقدام و بخش‌بندی مشخصات نزدیک‌تر شد؛ آزمون Chrome بعد از این تغییر کامل گذشت.
- صفحهٔ نگهداری پیشگیرانه ابتدا نمای همهٔ ماشین‌ها و خلاصهٔ موعد قطعات را نشان می‌دهد؛ ثبت گروهی سرویس نیز ابزارهای «انتخاب همه»، «هیچ‌کدام» و «فقط ثبت‌نشده‌ها» را دارد. ابزارهای ردیف جدولِ قدیمی هنوز موردبه‌مورد تطبیق داده نشده‌اند.
- جدول موعد نگهداری آخرین تاریخ سرویس/تعویض و فاصلهٔ باقی‌مانده یا گذشته از موعد را از دادهٔ API نمایش می‌دهد؛ build هر دو بخش موفق بود.
- پروندهٔ ماشین در React به تاریخچهٔ زمانی یکپارچهٔ رویدادهای مرحلهٔ تعمیر، تحلیل‌ها و کارکرد/سرویس متصل شد؛ API رویدادهای تعمیر را با کنترل مجوز و محدودهٔ ثبت‌مرحله برمی‌گرداند. خط زمانی تحلیل، نتیجهٔ اقدام، حساسیت، علت احتمالی و یادداشت را نشان می‌دهد؛ آزمون Chrome نمایش این جزئیات را تأیید کرد.
- آزمون مرورگر کامل پس از تغییر فرم خرابی و نمای ناوگان نگهداری دوباره اجرا شد و ورود، فهرست ماشین، ثبت/ویرایش دایرکتوری، نقش کاربر، وضعیت ناوگان، گردش تعمیر و پروندهٔ پیگیری پس از رد تست، بایگانی، قطعات، نگهداری، تحلیل، گزارش، پیامک شبیه‌سازی‌شده، پشتیبان، ماندگاری داده، منوی موبایل و خروج موفق بودند.
- گزارش تعمیرات اکنون علاوه بر جست‌وجو و بایگانی، فیلتر ماشین، بازهٔ تاریخ شمسی‌محور در منطقهٔ تهران، مرحله و فوریت دارد؛ build فرانت پس از تغییر موفق بود.
- تحلیل خرابی اکنون فیلترهای جست‌وجو، ماشین، بازهٔ تاریخ، حساسیت و نتیجه دارد؛ پاسخ‌های مربوط به راننده و مسئول PM با کلیدهای نسخهٔ اصلی ذخیره می‌شوند و نتیجهٔ پایه از آن‌ها محاسبه می‌شود. build فرانت موفق بود.
- در فرم تحلیل، پرسش گزارش‌دادن فقط وقتی نمایش داده می‌شود که پاسخ «قابل تشخیص بود» باشد؛ حساسیت هم از فهرست هم‌معنی نسخهٔ مرجع انتخاب می‌شود.
- فرم تحلیل حالا ماشین و افراد را از API مجازِ همان بخش می‌گیرد؛ به دسترسی جداگانهٔ تعمیرات وابسته نیست. مسئول‌های پیش‌فرض ماشین قابل تغییرند و در پاسخ‌های تحلیل ذخیره می‌شوند. اعتبارسنجی فرم به مرحلهٔ فعال محدود شد تا پرسش‌های پنهان مانع ادامهٔ فرم نشوند.
- پاسخ ثبت تحلیل کد ماشین و زمان ایجاد را مانند فهرست برمی‌گرداند؛ خروجی CSV/چاپ در صفحهٔ تحلیل اضافه و ایجاد، نمایش جزئیات و دانلود CSV در Chrome آزمایش شد.
- قواعد اقدام مدیریتی برای راننده و مسئول PM در تنظیمات قابل ویرایش و ذخیره شده‌اند؛ بازه‌ها در API اعتبارسنجی می‌شوند و در پایگاه داده و فضای سازگار نسخهٔ قبلی همگام می‌مانند.
- آزمون API ایزوله دریافت گزینه‌های تحلیل و ثبت یک تحلیل نمونه را هم گذراند؛ build فرانت و بک‌اند و بازسازی imageهای استقرار موفق بودند.
- اقدام مدیریتی تحلیل بر پایهٔ سابقهٔ همان فرد، حساسیت، پاسخ مربوطه و بازهٔ شمارش محاسبه می‌شود؛ قواعد ذخیره‌شدهٔ نسخهٔ سازگار خوانده می‌شوند و در نبود آن‌ها قواعد آغازین مرجع به کار می‌روند.
- صفحهٔ تحلیل اکنون خروجی CSV با محافظت در برابر فرمول‌های ناامن صفحه‌گسترده و چاپ مرورگر دارد.
- سربرگ React جست‌وجوی سراسری ماشین، پروندهٔ خرابی، تحلیل و قطعه با میان‌بر صفحه‌کلید و دکمهٔ ثبت سریع تحلیل/خرابی دارد؛ build فرانت پس از این تغییر موفق شد.
- فهرست کاربران هم جست‌وجو بر اساس نام/نام کاربری/موبایل و فیلتر فعال/غیرفعال دارد؛ build فرانت موفق بود.
- فهرست خرابی‌ها اکنون جست‌وجو و فیلتر ماشین، مرحله، فوریت و تاریخ دارد و تعداد نتایج را نشان می‌دهد؛ build فرانت موفق بود.
- فرم و API خرابی به تاریخ اعلام، مسئول تشخیص، موعد پیش‌بینی، نظر تعمیرکار و علت تأخیر گسترش یافت؛ تاریخ ارجاع و بازگشت هنگام ثبت مراحل ثبت می‌شود. migration دوازدهم افزایشی است و تاریخ پرونده‌های موجود را از زمان ثبت پر می‌کند.
- ویرایش پرونده نیز به API و فرم متصل است؛ نسخهٔ رکورد برای جلوگیری از بازنویسی تغییر هم‌زمان بررسی می‌شود و تاریخ اعلام/موعد با تاریخ ارجاع کنترل می‌شود.
- آزمون API با schema موقت، ساخت و ویرایش پرونده با فیلدهای تکمیلی و نمایش آن در گزارش را تأیید کرد؛ buildهای فرانت و بک‌اند موفق شدند.
- فهرست ماشین‌ها اکنون جست‌وجو بر اساس کد، پلاک، مدل و راننده، فیلتر فعال/غیرفعال و شمارش نتایج دارد؛ build فرانت موفق بود.
- تنظیمات نام واحد و پوستهٔ روشن/تیره/خودکار را هم ذخیره و به ظاهر پوسته و متن واحد در منو متصل می‌کند؛ buildهای فرانت و بک‌اند و آزمون API ایزوله موفق شدند.
- سناریوی مرورگر با Chrome و schema موقت، ورود، ساخت/ویرایش اطلاعات پایه و ماشین، گردش کامل خرابی و بایگانی، قطعات، آستانه‌های نگهداری، تنظیمات، گزارش، پیامک شبیه‌سازی‌شده، پشتیبان‌گیری سازگار، پایداری داده، منوی موبایل و خروج را گذراند.
- صفحهٔ وضعیت ناوگان با فیلتر مرحله، جست‌وجو، موعد گذشته، جزئیات/تاریخچه و ثبت گام بعد وصل شد. تعریف مراحل مشترک از تنظیمات به پرونده و مجوزهای کاربر می‌رسد؛ مسیر هر پرونده هنگام ثبت ثابت می‌ماند تا تغییر ترتیب فقط روی پرونده‌های تازه اثر کند.
- چهار الگوی پایهٔ دسترسی و گزینهٔ محدودهٔ تعمیرگاه اضافه شدند. APIهای وضعیت، فهرست پرونده‌ها، تاریخچه و گزارش برای کاربر محدود، پرونده‌های بیرون از مرحله‌های تعمیرگاه و فهرست همهٔ ماشین‌ها را برنمی‌گردانند.
- تست API اکنون تغییر ترتیب مراحل در زمان وجود پرونده و مسیر مستقل کاربر تعمیرگاه را هم می‌سنجد؛ مرورگر Chrome صفحهٔ وضعیت و تنظیم مراحل را بررسی می‌کند.
- تست رد سلامت و ساخت پروندهٔ تازهٔ پیوندخورده به ماشین/پروندهٔ قبلی در API و Chrome انجام شد؛ هر پروندهٔ ردشده فقط یک پروندهٔ پیگیری می‌پذیرد.
- آزمون مرورگر ابتدا دو ناسازگاری در خود آزمون/قرارداد را آشکار کرد: فیلدهای اختیاریِ مرحلهٔ تعمیر و انتظار نسخهٔ فضای سازگاری. همچنین مراحل گردش اشتباه شمرده شده بودند. قرارداد API و سناریوی مرورگر اصلاح و اجرای کامل بعدی موفق شد.
- اطلاعات IndexedDB کاربر خودکار روی سرور دیده نمی‌شود؛ باید در مرورگر مبدأ از نسخهٔ قدیمی JSON خروجی گرفته، در محیط آنلاین بازیابی و سپس از صفحهٔ مدیر «انتقال دادهٔ نسخهٔ قبلی» پیش‌نمایش و منتقل شود. انتقال واقعیِ فایل کاربر در این محیط انجام نشد چون فایل پشتیبان او موجود نیست.
- این پیاده‌سازی هنوز تطبیق پیکسل‌به‌پیکسل و کامل همهٔ صفحه‌های React با فایل مرجع نیست؛ موارد باقی‌ماندهٔ مهم در جدول حوزه‌ها مشخص شده‌اند.
- ۱۱ ماشین و ۹ پرسنل اولیه از seed کد نسخهٔ مرجع آمده‌اند؛ فضای سازگاری سرور و جدول‌های PostgreSQL پیش از seed خالی بودند. migration شمارهٔ ۱۱ این اطلاعات آغازین را فقط روی نصب خالی وارد می‌کند.
- کلید واقعی پیامک تنظیم نشده و هیچ پیام واقعی ارسال نشده است. پشتیبان‌گیری و بازیابی عملیاتی PostgreSQL نیز هنوز در استقرار تنظیم نشده است.
- در صفحهٔ نگهداری، ثبت یکجای سرویس اولیه برای چند قطعه اضافه شد؛ API آن اتمیک است و در آزمون ایزوله هم سرویس قطعات و هم کارکرد همراهش ذخیره و در تاریخچه دیده شدند. حذف سابقهٔ سرویس با تأیید کاربر و مجوز سمت سرور اضافه شد؛ Chrome هر دو مسیر ثبت و حذف را بررسی کرد.
- اطلاعات قطعه شامل نوع اقدام، توضیح و تبعات در API ایجاد/ویرایش شد. حذف قطعه با تأیید انجام می‌شود، جایگزین‌ها حذف می‌شوند و سابقهٔ سرویس با تصویر نام قطعه حفظ می‌ماند؛ migration افزایشی شمارهٔ ۲۱ این رابطه را برای نصب‌های موجود امن می‌کند.

- چیدمان فیلترهای باز و بایگانیِ خرابی با چینش RTL نسخهٔ مرجع هماهنگ شد: جست‌وجو پهن‌تر است، ذره‌بین دارد و فاصلهٔ اضافی زیر ورودی‌ها ندارد؛ در موبایل هم به دو ستون جمع می‌شود. زیرعنوان خرابی‌های جاری از نظر نقطه‌گذاری با متن مرجع یکی است. آزمون Chrome وجود ذره‌بین/فیلتر تأخیر و نبود اسکرول افقی در موبایل را می‌سنجد.

- بازبینی تصویری مدیر در Chrome با مرورگر ایزوله و مدیر موقت محلی، صفحات قدیمی کاربران و پیامک را قابل مشاهده کرد؛ تصویرها در `frontend/visual-legacy-admin-users.png` و `frontend/visual-legacy-admin-sms.png` هستند و حساب آزمایشی بیرون از مرورگر آزمون باقی نمی‌ماند. صفحهٔ React کاربران با مرجع هم‌راستا شد: فیلتر اضافه حذف، آواتار/هشدار/ستون‌ها/نشان مدیر/پاصفحه هماهنگ و ستون آخرین ورود واقعی شد. migration ۳۰ و API زمان ورود موفق را در PostgreSQL ذخیره می‌کنند. buildها موفق؛ اجرای Chrome پس از این تغییر در حال بررسی است.
- صفحهٔ پیامک با نسخهٔ مرجع هم‌ساختار شد: پیش‌نمایش گوشی، وضعیت سرویس/ارسال آزمایشی، فهرست گیرنده‌ها، جدول قواعد هر مرحله و گزارش در بلوک‌های متناظر قرار گرفتند؛ انتخاب ردیف، فعال‌سازی مرحله، گیرنده، ویرایش قالب، ذخیرهٔ مشترک، شبیه‌ساز و تلاش مجدد حفظ شدند. API جدید `/api/v1/sms/recipients` مجوز پیامک را الزام می‌کند و فقط نام، نقش و شمارهٔ گیرندگان مرتبط را برمی‌گرداند. قرارداد OpenAPI و گردش کامل Chrome این مسیر را بررسی می‌کنند؛ ارسال واقعی همچنان خارج از دامنه است.
- اجرای توسعهٔ واقعی روی همین دستگاه هم بررسی شد: PostgreSQL محلیِ پروژه روی پورت ۵۵۴۳۳ بالا آمد و `dev.bat` طوری اصلاح شد که در صورت وجود خوشهٔ `.dev-postgres` از آن استفاده کند؛ دیگر برخورد پورت ۵۵۴۳۲ با برنامه‌های دیگر مانع اجرا نیست. API آماده و فرانت با عنوان «سامانه ناوگان سپید» از پورت‌های توسعه پاسخ دادند. پایگاه تازه بود؛ مدیر آزمایشی محلی ساخته و ورود نشست API تأیید شد. اجرای Chrome جامع هم پس از بازچینی کاربران/پیامک و migration ۳۰ موفق است. این محیط توسعه است؛ دامنه/HTTPS، دادهٔ واقعی نسخهٔ قدیمی و پذیرش سرور مقصد همچنان وابستگی بیرونی‌اند.
- اتصال اجرای زندهٔ backend به همان پایگاه محلیِ ۵۵۴۳۳ اصلاح شد؛ پیش از آن یک فرایند قدیمی به اتصال دیگری اشاره می‌کرد. در Chrome مدیر اولیه ساخته شد، صفحات کاربران و پیامک باز شدند و ورود عادی همان حساب از API با نقش مدیر کل تأیید شد. باگ بازگشت نادرست فرم راه‌اندازی پس از خروج رفع شد و به آزمون جامع اضافه شد.
- توضیح سربرگ پیامک حالا شرط روشن‌بودن ارسال خودکار و قراردادن پیام در صف را می‌گوید؛ Chrome smoke این متن و شبیه‌سازی بدون ارسال واقعی را بررسی می‌کند.
- build فرانت و بک‌اند، آزمون مستقل API و آزمون جامع Chrome پس از اصلاح خروج/ورود مدیر و متن پیامک همگی موفق‌اند؛ سلامت محیط توسعهٔ زنده ۲۰۰/`ready` است. Compose تولید فقط از نظر پیکربندی معتبر شد و هنوز روی میزبان واقعی اجرا/پذیرفته نشده است.
