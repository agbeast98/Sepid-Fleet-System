# استقرار با Docker Compose

این بسته پنج سرویس دارد: PostgreSQL داخلی شبکهٔ Docker، API بک‌اند، worker مستقل پیامک، فرانت‌اند Nginx و پشتیبان‌گیر زمان‌بندی‌شده. پایگاه‌داده و فایل‌های پشتیبان به شبکهٔ بیرونی منتشر نمی‌شوند و وب فقط روی `127.0.0.1:8080` گوش می‌دهد تا پشت reverse proxy دارای HTTPS قرار بگیرد. Nginx تا آماده‌شدن پاسخ سلامت API شروع به سرویس‌دهی نمی‌کند؛ API پیامک را در صف پایدار می‌گذارد و worker جداگانه صف را پردازش می‌کند.

۱. فایل `.env.production.example` را در پوشهٔ `deploy` به `.env.production` کپی کنید. رمزهای یکتا بسازید؛ رمز PostgreSQL را در `DATABASE_URL` هم URL-encode کنید.
۲. `DATABASE_URL` را با نام کاربری، رمز، میزبان `postgres` و نام پایگاه‌دادهٔ همان فایل هماهنگ کنید.
۳. پیش از ساخت، تنظیمات Compose را اعتبارسنجی کنید: `docker compose --env-file deploy/.env.production -f deploy/compose.yaml config --quiet`.
۴. از ریشهٔ پروژه اجرا کنید: `docker compose --env-file deploy/.env.production -f deploy/compose.yaml up -d --build`.
۵. سلامت سرویس‌ها را ببینید: `docker compose --env-file deploy/.env.production -f deploy/compose.yaml ps` و سپس `Invoke-RestMethod http://127.0.0.1:8080/api/v1/health/ready` را در PowerShell اجرا کنید؛ پاسخ باید `ready` باشد.
۶. reverse proxy میزبان را به `http://127.0.0.1:8080` وصل و HTTPS، دامنه و تمدید گواهی را در همان لایه فعال کنید.

ساخت imageهای API و وب در این رایانه بررسی شده است. API از Argon2 داخلی Node.js استفاده می‌کند؛ بنابراین Node.js 24.7 یا بالاتر از شاخهٔ 24 لازم است و Dockerfileها همین شاخه را به کار می‌برند. اگر Docker Hub از شبکهٔ مقصد در دسترس نبود، پراکسی Docker Desktop یا روش انتقال image از میزبان build را تنظیم کنید.

API هنگام بالا آمدن migrationها را اجرا می‌کند. متغیرهای ساخت مدیر فقط در اولین اجرا حساب را می‌سازند و پس از آن رمز مدیر را تغییر نمی‌دهند؛ بعد از ساخته‌شدن حساب، متغیرهای موقت مدیر را از فایل محیطی حذف کنید.

در محیط توسعه، اگر مدیرکل هنوز ساخته نشده باشد، صفحهٔ ورود فرم راه‌اندازی اولیه را نشان می‌دهد؛ ایجاد اولین مدیر در یک تراکنش قفل‌شده انجام می‌شود و پس از آن مسیر برای همیشه بسته می‌ماند. در استقرار production این راه‌اندازی عمومی به‌طور پیش‌فرض خاموش است. مدیر را با متغیرهای محیطیِ شروع نخست بسازید یا فقط در زمان راه‌اندازی کنترل‌شده `SEPID_ALLOW_ADMIN_SETUP=true` را فعال کنید و بلافاصله پس از ساخت مدیر آن را خاموش و API را بازراه‌اندازی کنید. این گزینه را روی سامانهٔ عمومیِ بدون محدودسازی شبکه فعال نگذارید.

پس از آماده‌شدن API، سرویس `backup` یک فایل PostgreSQL با قالب قابل‌بازیابی می‌سازد، ساختار dump را با `pg_restore --list` اعتبارسنجی می‌کند و نسخه‌های قدیمی‌تر از مدت نگه‌داری را حذف می‌کند. فایل موقت تا پایان اعتبارسنجی پسوند `.tmp` دارد و وارد فهرست نسخه‌های معتبر نمی‌شود. فاصله و نگه‌داری با `BACKUP_INTERVAL_SECONDS` و `BACKUP_RETENTION_DAYS` تنظیم می‌شوند؛ پیش‌فرض روزانه و ۱۴ روز است. فایل‌ها در volume جداگانهٔ `sepid-production-backups` ذخیره می‌شوند. API این volume را فقط‌خواندنی می‌بیند و بخش «پشتیبان‌های سرور» در پنل فقط برای مدیرکل قابل‌دسترسی است؛ فایل‌ها شامل کل داده‌های سازمان هستند و باید محرمانه نگه داشته شوند.

برای دیدن فهرست و گزارش سرویس:

```sh
docker compose --env-file deploy/.env.production -f deploy/compose.yaml exec backup ls -lh /backups
docker compose --env-file deploy/.env.production -f deploy/compose.yaml logs --tail=50 backup
```

این volume جداست اما هنوز روی همان میزبان قرار دارد؛ برای پشتیبان واقعی، از آن به فضای خارج از میزبانِ کنترل‌شده نسخه‌برداری کنید و دسترسی آن مقصد را محدود کنید. پیش از بهره‌برداری، یک dump را در پایگاه آزمایشی جدا بازیابی و صحت برنامه را پس از بازیابی بررسی کنید. اعتبارسنجی فهرست dump جای تمرین بازیابی کامل را نمی‌گیرد. پیامک تا زمان افزودن کلید واقعی در حالت شبیه‌سازی می‌ماند.

برای تمرین بازیابی یک فایل روی رایانهٔ ویندوزی که Docker آن روشن است، ابتدا یک فایل پشتیبان را به‌صورت امن دریافت کنید و سپس از ریشهٔ پروژه اجرا کنید:

```powershell
.\deploy\verify-backup.ps1 -BackupFile 'D:\secure-backups\sepid-20261113T120000Z.dump'
```

این بررسی یک کانتینر موقت PostgreSQL 16 بدون پورت منتشرشده و بدون شبکه می‌سازد، فایل را واقعاً بازیابی می‌کند، وجود جدول‌های اصلی و شمار رکوردها را می‌سنجد و در پایان کانتینر موقت را پاک می‌کند. پایگاه اصلی و volumeهای آن را لمس نمی‌کند. اجرای آن به Docker فعال و دریافت image `postgres:16-alpine` نیاز دارد. این بررسی را برای یک فایل کپی‌شده از پشتیبان خارج از میزبان هم انجام دهید؛ آزمون کامل برنامه و صحت داده‌های سازمان پس از بازیابی همچنان باید در محیط آزمایشی خودتان انجام شود.

در پنل مدیرکل، بخش «پشتیبان‌های سرور» فهرست نسخه‌ها و امکان دریافت امن فایل را ارائه می‌کند. این صفحه پشتیبان‌گیری فوری یا بازیابی انجام نمی‌دهد؛ این عملیات عمداً در چرخهٔ استقرار/رویهٔ عملیاتی باقی می‌ماند.
