# سورس سامانه ناوگان — شرکت دام و طیور سپید بستک

راهنمای تحویل به واحد برنامه‌نویسی برای آنلاین کردن سامانه.

---

## ۱. سامانه چیست

یک برنامهٔ تک‌صفحه‌ای (SPA) کاملاً سمت مرورگر است:

- **بدون فریم‌ورک و بدون وابستگی**: JavaScript خالص (Vanilla JS)، بدون npm، بدون مرحلهٔ build.
- مسیریابی با hash (`#/dashboard`، `#/repairs/<id>` و …).
- تقویم شمسی، نمودارها، چاپ، جست‌وجو و آیکون‌ها همه داخل خود کد نوشته شده‌اند.
- فونت وزیرمتن (Vazirmatn) به‌صورت فایل محلی همراه پروژه است؛ هیچ درخواستی به اینترنت (CDN) ارسال نمی‌شود.

## ۲. ساختار پوشه

```
sepid-fleet-system/
├── index.html                  ← صفحهٔ اصلی (فقط اسکلت؛ همه چیز را app.js می‌سازد)
├── assets/
│   ├── css/style.css           ← همهٔ استایل‌ها (حالت روشن/تیره، چاپ، موبایل)
│   ├── js/app.js               ← کل منطق برنامه (~۷۰۰۰ خط)
│   └── fonts/Vazirmatn-*.woff2 ← وزن‌های 400 تا 800
├── original/
│   └── fleet-single-file.html  ← همان فایل تکی فعلی (نسخهٔ آفلاین، دست‌نخورده)
└── README.md
```

برای اجرای محلی کافی است پوشه را با یک وب‌سرور ساده باز کنید، مثلاً:

```
python -m http.server 8000
```
و سپس `http://localhost:8000` را باز کنید.

## ۴. داده‌ها الان کجا ذخیره می‌شوند

- **همهٔ داده‌ها یک شیء JSON واحد** است که در IndexedDB مرورگر ذخیره می‌شود:
  پایگاه `fleet-maint-app` ← store `kv` ← کلید `db`.
- store دوم `snapshots`: آخرین ۲۰ نسخهٔ داخلی (روزانه و پیش از بازیابی).
- اگر IndexedDB نباشد، به `localStorage` با پیشوند `fma:` برمی‌گردد.
- نشست ورود (`fma:session`) و شمارش رمز اشتباه (`fma:lock:*`) در `localStorage` است.

کلیدهای سطح اول دادهٔ اصلی (`schema: 4`):

```
settings   تنظیمات، مراحل، تنظیمات پیامک، شمارنده‌ها
rules      قوانین اقدامات مدیریتی
people     پرسنل (راننده، سرپرست، PM)
machines   ماشین‌آلات
models     مدل‌ها
catalog    قطعات جایگزین هر مدل
analyses   تحلیل‌های خرابی
partLogs   سوابق تعویض/سرویس قطعات
odoLogs    سوابق کیلومتر/ساعت‌کار
repairs    خرابی‌ها و مراحل وضعیت (تاریخچهٔ کامل هر ماشین)
users      کاربران، هش رمز، دسترسی‌ها
smsLog     گزارش پیامک‌ها
```

همهٔ تغییرات از تابع `Store.update(fn)` عبور می‌کنند؛ یعنی فقط یک نقطه برای ذخیره‌سازی وجود دارد.

## ۵. ⚠️ نکتهٔ مهم: آپلود همین فایل‌ها روی هاست = چندکاربره نمی‌شود

اگر همین پوشه را روی یک هاست بگذارید، صفحه باز می‌شود و کار می‌کند، **اما داده‌های هر کاربر فقط در مرورگر خودش ذخیره می‌شود** و هیچ کاربری کار دیگری را نمی‌بیند. برای این‌که سرپرست، تعمیرکار و مدیر روی یک دادهٔ مشترک کار کنند، **سمت سرور (Backend) و پایگاه داده لازم است.**

همچنین IndexedDB به دامنه وابسته است؛ داده‌های فعلیِ نسخهٔ آفلاین خودبه‌خود به نسخهٔ آنلاین منتقل نمی‌شوند (روش انتقال در بند ۷).

## ۶. کارهایی که برای آنلاین شدن لازم است

### الف) سرور و پایگاه داده
هر زبانی قابل استفاده است (PHP/Laravel + MySQL، Node.js، ASP.NET و …). دو راه:

**راه سریع (حداقل تغییر در فرانت):**
- دو API: `GET /api/db` (خواندن کل JSON) و `PUT /api/db` (ذخیرهٔ کل JSON).
- در `Store`، توابع `init` و `persistNow` به‌جای `kvGet('db')`/`kvSet('db')` این APIها را صدا بزنند.
- **کنترل همزمانی الزامی است**: هر ذخیره یک شمارهٔ نسخه بفرستد و سرور اگر نسخه قدیمی بود `409` برگرداند تا تغییر کاربر دیگر پاک نشود.
- برای دیدن تغییرات دیگران: polling هر چند ثانیه یا SSE/WebSocket و سپس صدا زدن listenerهای `Store.onChange`.
- محدودیت: چون کل داده یک بلوک است، با زیاد شدن داده و کاربران، تداخل و حجم انتقال زیاد می‌شود.

**راه اصولی (پیشنهادی برای بلندمدت):**
- هر کلید سطح اول (machines، repairs، people، …) یک جدول جدا، با API جدا برای افزودن/ویرایش/حذف هر رکورد.
- مراحل وضعیت داخل `repairs` به‌صورت جدول تاریخچه (هر ثبت یک ردیف با کاربر و زمان).

### ب) ورود و دسترسی‌ها باید به سرور منتقل شود (امنیتی)
- الان هش رمزها (SHA-256 با salt، ۲۰۰۰ دور — تابع `hashPass`) **داخل همان دادهٔ مشترک** است. اگر کل JSON برای همه ارسال شود، هش رمز همهٔ کاربران به مرورگر همه می‌رسد.
- بررسی دسترسی‌ها الان فقط در مرورگر است (`Auth.pre` / `Auth.post` در `Store.update`) و با ابزار توسعه‌دهنده قابل دور زدن است.
- لازم است: ورود سمت سرور (session یا JWT، هش bcrypt/argon2)، و **بررسی سطح دسترسی هر بخش و مراحل مجاز هر کاربر روی سرور**. ساختار دسترسی‌ها در `SECTIONS` و `PERM_TEMPLATES` (حوالی خط 5512) آمده است: سطح ۰ تا ۳ برای هر بخش + فهرست مراحل مجاز.
- `users` (به‌خصوص `hash` و `salt`) هرگز نباید در پاسخ API به مرورگر برود.
- فقط کاربر مدیر کل (`super: true` — آرمین جمالی) کاربر می‌سازد و دسترسی می‌دهد.

### ج) پیامک باید از سرور ارسال شود
- الان ماژول `SMS` مستقیماً از مرورگر به کاوه‌نگار یا sms.ir درخواست می‌دهد و **کلید API در تنظیمات داخل داده ذخیره است** (قابل دیدن برای همه + مشکل CORS).
- لازم است: کلید API فقط روی سرور باشد؛ وقتی یک مرحلهٔ وضعیت ثبت شد (`SMS.onStage` — خطوط 4528 و 6547)، سرور پیامک را برای سرپرست بفرستد و در `smsLog` ثبت کند.
- خرید پنل پیامک پیش‌نیاز ارسال واقعی است.

### د) پشتیبان‌گیری
- `snapshots` و `AutoBackup` (پشتیبان در پوشهٔ ویندوز) در نسخهٔ آنلاین با پشتیبان‌گیری خودکار پایگاه دادهٔ سرور جایگزین می‌شوند.
- دکمهٔ «دریافت فایل پشتیبان» (خروجی JSON) را می‌توان نگه داشت.

### هـ) زیرساخت
- **HTTPS الزامی** است (رمز عبور ارسال می‌شود).
- هاست داخل ایران برای دسترسی پایدار کاربران و پنل پیامک مناسب‌تر است.
- کاربران تعمیرات در شهر دیگری هستند؛ صفحه برای موبایل هم طراحی شده است.

## ۷. انتقال داده‌های فعلی به نسخهٔ آنلاین

1. در نسخهٔ آفلاین فعلی، با کاربر مدیر کل وارد شوید ← بخش «پشتیبان‌گیری» ← «دریافت فایل پشتیبان».
2. فایل JSON خروجی دقیقاً همان ساختار بند ۴ را دارد (به‌همراه `exportedAt`).
3. این فایل یک‌بار در پایگاه دادهٔ سرور وارد (import) شود.
4. تابع `migrate()` در `Store` داده‌های نسخه‌های قدیمی‌تر را به `schema: 4` ارتقا می‌دهد؛ اگر داده به جدول‌ها شکسته می‌شود، بهتر است قبل از import یک‌بار از این تابع عبور کند.
